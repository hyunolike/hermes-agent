# 이어 묻기 스트리밍

- 날짜: 2026-09-21
- 상태: 설계 확정, 구현 전
- 범위: `/agent/ask` 의 스트리밍 변형, `llm` 포트 확장, 프론트 `AskBox`

## 왜

이어 묻기는 이미 있다. `AskBox` 가 멀티턴 대화를 들고 `/agent/ask` 에 보내고, 답변마다
인용 칩을 붙인다. 부족한 것은 속도다 — 답변이 완성될 때까지 아무것도 안 보이다가 한꺼번에
뜬다. 실측으로 4.7~6.9초다.

## 무엇이 부딪히는가

이 서비스의 약속은 **번들에 없는 문서를 인용한 설명은 통째로 내보내지 않는다**는 것이다.
`CitationValidator` 는 완성된 답변의 인용을 보고 판정한다. 스트리밍은 답변이 완성되기
전에 글자를 화면에 보낸다. 끝에 가서 인용이 틀렸다는 것을 알았을 때 사용자는 이미 문장을
읽은 뒤다.

"바로 흘리고 틀리면 지운다"는 이 약속을 정면으로 깬다. 그래서 채택하지 않는다.

## 사전 검증 (2026-09-21, 스파이크)

출력 스키마는 SDK 가 `Explanation` 에서 유도하며 이미 `citations` 를 `explanation` 보다
앞에 둔다. 운영 모델이 스트리밍에서도 그 순서를 지키는지 쟀다. raw HTTP, strict
`json_schema`, `gpt-4o`, 실제 번들과 픽스처로 3회.

```
[1] citations 먼저 | 첫토큰 2.87s | 인용완성 3.33s | 본문시작 3.50s | 전체 6.91s
[2] citations 먼저 | 첫토큰 1.42s | 인용완성 1.69s | 본문시작 1.73s | 전체 4.73s
[3] citations 먼저 | 첫토큰 0.84s | 인용완성 1.07s | 본문시작 1.11s | 전체 5.40s
```

3/3 인용이 먼저 왔고, 인용 배열은 첫 토큰 뒤 0.2~0.5초면 닫혔다. 인용을 검증한 뒤 본문을
흘리면 첫 글자가 보이는 시점이 **4.7~6.9초에서 1.1~3.5초로** 당겨진다.

**아직 모르는 것:** Anthropic 과 OpenRouter 는 재지 않았다. 표본이 3이다. 스파이크는
raw HTTP 로 했으므로 Spring AI 의 `ChatClient.stream()` 이 스트리밍 모드에서도
`response_format` 을 싣는지는 따로 확인해야 한다 — 루프백 캡처로 무료로 된다.

## 설계

### 원칙 — 안전은 필드 순서에 의존하지 않는다

스파이크가 인용이 먼저 온다는 것을 보였지만, 그것에 안전을 걸지는 않는다.

- **인용이 먼저 오면** 배열이 닫히는 순간 검증하고, 통과했으면 이어지는 본문을 흘린다
- **본문이 먼저 오면** 본문을 버퍼에 쌓고, 끝에서 인용을 검증한 뒤 한꺼번에 보낸다

어느 쪽이든 **검증을 통과하지 않은 글자는 한 글자도 나가지 않는다.** 필드 순서는 속도만
좌우하고 안전은 좌우하지 못한다. 이 성질이 이 설계의 전부이고, 테스트로 못 박는다.

### 포트 확장

`ExplanationProvider` 에 스트리밍 메서드를 더한다.

```kotlin
fun stream(systemText: String, userText: String, onChunk: (String) -> Unit): StreamEnd

sealed interface StreamEnd
data class StreamCompleted(val usage: ProviderUsage) : StreamEnd
data class StreamRefused(val category: String?) : StreamEnd
data class StreamFailed(val reason: String) : StreamEnd
```

**포트를 거치는 이유:** 스트리밍 경로가 포트를 우회하면 비스트리밍 경로와 다른
`systemText`/`userText` 를 조립할 여지가 생긴다. 같은 프롬프트로 조립되어야 하네스가 잰
숫자가 스트리밍 경로에도 유효하다.

**Reactor 를 포트에 올리지 않는 이유:** 포트가 존재하는 이유 중 하나는 서비스 계층과
테스트 페이크가 Spring AI 없이 돌게 하는 것이다. `Flux` 를 시그니처에 올리면 그 성질이
깨진다. 블로킹 호출이 조각마다 콜백을 부르는 형태로 두고, Reactor 는
`SpringAiExplanationProvider` 안에 가둔다.

### 스트림 파서

모델은 JSON 문자열을 조각으로 보낸다. `AskStreamParser` 는 조각을 받아 이벤트를 내는
**순수한 상태 기계**다. 네트워크도 Spring 도 모른다.

해야 할 일:

1. `"citations":[...]` 배열이 닫히는 순간을 감지해 파싱한다
2. 이어지는 `"explanation":"..."` 의 **문자열 내용만** 꺼낸다
3. JSON 이스케이프(`\n`, `\"`, `\\`, `\uXXXX`)를 **조각 경계를 넘어** 푼다 —
   `\u` 가 한 조각, `AC00` 이 다음 조각에 오는 경우가 실제로 생긴다. 한글은 전부
   `\uXXXX` 이거나 멀티바이트라, 여기서 틀리면 사용자가 깨진 글자를 본다
4. 본문이 먼저 오면 원칙대로 버퍼에 쌓는다

검증 자체는 파서가 하지 않는다. 파서는 "인용 배열이 완성됐다"는 사실과 그 내용만 알리고,
기존 `CitationValidator` 가 판정한다. 검증 규칙이 두 군데 생기면 갈라진다.

### 엔드포인트

`POST /agent/ask/stream` — SSE. 요청 본문은 `/agent/ask` 와 같다(`courseUuid`,
`question`, `history`). 사실은 여전히 백엔드에서만 온다.

기존 `POST /agent/ask` 는 **그대로 둔다.** 비스트리밍 계약이고 하네스와 기존 테스트가
거기 걸려 있다.

웹 스택이 servlet(webmvc)이므로 `SseEmitter` 로 응답한다. 포트의 블로킹 `stream(...)`
호출은 요청 스레드가 아니라 별도 실행기에서 돈다.

### 이벤트 계약

| 이벤트 | 언제 | 내용 |
| --- | --- | --- |
| `citations` | 인용 배열이 완성되고 **검증을 통과한 직후** | 경로 목록 |
| `delta` | 검증 통과 후 본문 조각이 올 때마다 | 텍스트(이스케이프가 풀린) |
| `done` | 정상 종료 | `generatedAt`, `model` |
| `unavailable` | `delta` 를 **하나도 보내기 전의** 모든 실패 — 인용 무효, 거절, 사실 조회 실패, 첫 본문 전 스트림 실패 | 사유 |
| `aborted` | `delta` 를 **보내기 시작한 뒤의** 실패 — 본문 도중 스트림이 끊김 | 사유 |

실패 이벤트를 둘로 나눈 이유: 두 경우의 불변식이 다르다.

- **`unavailable` 이 오면 그 전에 `delta` 는 0개다.** 이것이 원칙의 관측 가능한 형태이고,
  인용이 무효인 경우는 반드시 여기로 온다 — 인용은 본문보다 먼저 검증되거나(인용 먼저),
  본문을 버퍼에 가둔 채 검증되므로(본문 먼저) 무효 인용이 `delta` 뒤에 발견될 길이 없다
- **`aborted` 앞의 `delta` 는 인용 검증을 통과한 본문이지만 문장이 미완이다.** 안전
  문제는 아니다. 그래도 미완 문장을 설명으로 남기지 않는다

한 이벤트로 합치면 "`unavailable` 이면 `delta` 0개"라는 문장이 거짓이 되고, 그 문장을
믿고 짠 클라이언트는 미완 본문을 화면에 남긴다.

인용 칩이 본문보다 먼저 화면에 뜬다. 출처가 먼저 보이고 그다음 설명이 흐른다.

### 프론트

`EventSource` 는 POST 를 못 하므로 `fetch` + `ReadableStream` 으로 SSE 를 읽는다.
`AskBox` 는 `citations` 에서 칩을 그리고, `delta` 마다 본문을 이어 붙이고, `unavailable`
이면 기존 실패 상태로 간다.

`aborted` 를 받거나, `done` 없이 연결이 끊기면 받은 본문을 **남기지 않는다.** 두 경우 모두
본문은 인용 검증을 통과했지만 문장이 미완이다. 미완 문장을 설명으로 보여 주지 않고 실패
상태로 간다. 클라이언트가 본문을 확정하는 조건은 **`done` 을 받았을 때 하나뿐이다.**

## 테스트

`CapturingEndpoint` 가 **미리 짠 SSE 스트림을 돌려주게** 확장한다. 그러면 키 없이
결정론적으로 검사할 수 있다.

| 입력 | 기대 |
| --- | --- |
| 인용 먼저 + 유효 | `citations` 뒤 `delta` 들, `done` |
| 인용 먼저 + **무효** | `unavailable`, **`delta` 0개** |
| **본문 먼저** + 유효 | 끝에서 `citations` 와 본문이 한 번에, `done` |
| **본문 먼저** + 무효 | `unavailable`, **`delta` 0개** |
| `\uXXXX` 가 조각 경계에 걸림 | 한글이 깨지지 않고 나감 |
| `\"` 와 `\\` 가 조각 경계에 걸림 | 원문 그대로 |
| 거절 | `unavailable` |
| 본문 도중 스트림 끊김 | `delta` 몇 개 뒤 **`aborted`** (`unavailable` 아님) |

둘째와 넷째가 핵심이다 — **검증 안 된 글자가 새지 않는다**를 증명한다. 파서는 순수
함수라 조각 경계를 한 글자 단위로 쪼개 모든 위치에서 돌려 볼 수 있다.

스트리밍 모드의 요청 본문이 `stream: true` 와 `response_format` 을 **둘 다** 싣는지도
루프백 캡처로 고정한다. 스파이크가 raw HTTP 로 증명한 것을 Spring AI 경로에서 다시
증명하는 자리다.

## 하지 않는 것

- **첫 설명(`/agent/explain`) 스트리밍** — 대화형 화면이 이득이 가장 크다. 첫 설명은
  이 설계가 검증된 뒤 같은 파서로 붙인다
- **대화 저장** — 여전히 클라이언트가 들고 있다. "DB 없음" 전제를 유지한다
- **프롬프트 변경** — 요청 바이트는 그대로다. 1시간 캐시가 유지된다
- **`/agent/ask` 제거** — 비스트리밍 경로는 남는다
- **Anthropic/OpenRouter 의 필드 순서 보증** — 원칙 덕에 필요하지 않다. 순서가 달라도
  안전하고 느려질 뿐이다
